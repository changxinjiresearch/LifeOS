# NextPlan Sync Command Protocol v1

Status: **FROZEN FOR PHASE A2**

Version: `1.0`

This protocol defines how the NextPlan Thin Bridge, Railway cloud classifier and canonical event layer communicate. It sits on top of `NEXTPLAN_CORE_SCHEMA_V1.md`.

## 1. Goals

The protocol must provide:

- one deterministic command envelope for all sync candidates;
- backward-compatible support for the v0.5.0 Thin Bridge;
- explicit confidence and confirmation semantics;
- idempotent or semantically idempotent writes;
- a normalized execution receipt;
- no business-rule dependence on locally installed classifier files.

## 2. Flow

```text
ChatGPT turn
  -> Thin Bridge
  -> POST /extension/classify
  -> Candidate Command
  -> auto-sync OR confirmation queue
  -> POST /extension/action
  -> append-only NextPlan event
  -> state builder
  -> canonical state.json
  -> Execution Receipt
```

The browser extension is a transport/UI bridge. Business logic belongs in the Railway cloud layer.

## 3. Candidate Command envelope

Canonical response from `/extension/classify`:

```json
{
  "protocol_version": "1.0",
  "id": "candidate-uuid",
  "intent": "update_project",
  "kind": "direct_project_edit",
  "confidence": 0.99,
  "label": "更新项目：NextPlan开发",
  "reason": "检测到明确项目变更",
  "target": {
    "entity_type": "project",
    "entity_id": "project-item-daed6c"
  },
  "confirmation": {
    "required": false,
    "destructive": false
  },
  "action": {
    "operation_id": "candidate-uuid",
    "action": "update_project_snapshot",
    "project_id": "project-item-daed6c"
  }
}
```

For v0.5.0 compatibility the following legacy aliases remain present when applicable:

- `kind`
- `destructive`
- `requiresConfirmation`
- `informational`

## 4. Confirmation policy

A candidate may auto-sync only when all are true:

- it has a writable action;
- `confirmation.required = false`;
- `confirmation.destructive = false`;
- confidence is at or above the configured auto-sync threshold;
- no unresolved entity ambiguity remains.

Confirmation is required for:

- destructive deletion;
- a meaningful ambiguous entity match;
- a command that would overwrite a conflicting canonical value;
- any operation whose intent is not explicit enough for safe execution.

Informational/no-op candidates are never written.

## 5. Operation ID

Every writable candidate carries an `operation_id`.

Rules:

- `operation_id` is generated by the cloud classifier and copied into the action payload.
- retries should preserve the same operation id when the same queued candidate is retried;
- operations should be semantically idempotent even if the underlying event id differs;
- future protocol revisions may bind operation ids directly to immutable event ids for strict exactly-once semantics.

## 6. Action vocabulary

Supported action names in protocol v1 include:

- `create_project`
- `update_project_snapshot`
- `update_project`
- `delete_project`
- `create_task`
- `update_milestone`
- `complete_task`
- `delete_task`
- `set_deadline`
- `upsert_calendar_event`

The command envelope may be extended without changing the Thin Bridge as long as the Railway backend understands the new action.

## 7. Entity target

When known, the candidate contains:

```json
{
  "target": {
    "entity_type": "project | task | deadline | calendar_event | note | resource",
    "entity_id": "stable-id"
  }
}
```

For creation operations `entity_id` may be omitted before execution.

Phase A3 defines entity resolution and ambiguity handling in detail.

## 8. Execution Receipt

Canonical response from `/extension/action`:

```json
{
  "receipt_version": "1.0",
  "status": "applied",
  "operation_id": "candidate-uuid",
  "operation": "update_project_snapshot",
  "entity_type": "project",
  "entity_id": "project-item-daed6c",
  "event_id": "evt-...",
  "summary": "Updated project-item-daed6c",
  "commit_sha": "optional-git-sha"
}
```

Allowed high-level statuses:

- `applied`
- `accepted_pending_builder`
- `no_change`
- `already_exists`
- `already_absent`
- `needs_confirmation`
- `rejected`
- `error`

Legacy operation-specific fields may remain in a receipt for compatibility.

## 9. Error contract

HTTP errors use:

```json
{
  "error": "machine_readable_code",
  "detail": "safe human-readable explanation"
}
```

Sensitive backend values, tokens and secrets must never be returned.

## 10. Idempotency expectations

Protocol v1 requires semantic idempotency:

- create operations check for existing same-identity entities;
- update operations return `no_change` when the canonical value is already present;
- completion is safe to replay;
- deletion may return `already_absent`;
- calendar/deadline writes use stable logical identifiers where possible;
- local turn fingerprints prevent repeated automatic processing of the same browser turn.

## 11. Backward compatibility

The Thin Bridge v0.5.0 must continue working during Phase A. Therefore:

- `/extension/classify` continues returning a `candidate` object;
- legacy `requiresConfirmation`, `destructive`, `informational`, `kind` remain available;
- `/extension/action` continues accepting the existing flat action payload;
- normalized receipt fields are additive.

This allows cloud-side protocol evolution without another local extension replacement.
